# 작은 TPS 성능 분석 요약 (Phase 4, 2026-10-18 ~ 10-21)

## 한 줄 요약

**병목 측정에서 출발해 원인 특정 → 엔진 소스로 검증 → 최적화 채택 → 업스케일러·품질 단계 비교까지 이어 갔고, 모든 결과가 "GPU의 그래픽 큐가 프레임의 임계 경로이고 비동기 컴퓨트에는 약 4 ms 여유가 있다"는 한 가지 사실로 설명된다는 것을 Unreal Engine 5.8 패키지 실측으로 보였습니다.**

- **진단(P1~P4-02):** 1440p 기준에서 GPU 병목을 확인하고 텍스처·그림자 설정을 바로잡은 뒤, 적을 5 → 20 → 50명으로 늘려 CPU와 GPU 비용을 나눠 추적했습니다. 적 수에 비례하는 GPU 비용의 약 70%가 적 스키닝 메시의 레이 트레이싱(RT) 갱신이었습니다.
- **개선(P4-03~P4-05):** RT용 LOD 낮추기가 오히려 손해인 이유를 엔진 소스에서 찾고(스키닝 두 번), 적 메시만 RT에서 빼는 변경을 채택했습니다(적 50명 GPU −4.7%).
- **비교(P5~P7):** DLSS SR·RR과 품질 프리셋을 같은 방법으로 비교했습니다. 해상도를 낮추는 것보다 기능 단계를 낮추는 쪽이 효과가 컸고(Medium GPU −24%, 화질 허용 가능), 그 이유도 그래픽 큐 임계 경로로 설명됩니다.

**환경:** i5-14600K, RTX 4070 Ti SUPER(16 GB), Windows 11, UE 5.8.2(D3D12, SM6). 출력 2560×1440, 업스케일러 TSR(Temporal Super Resolution) 내부 해상도 60.6%(1552×873), Lumen 하드웨어 RT, 품질 Epic. 기준 장면 Frame 약 13 ms(GPU 약 12 ms)로 GPU 병목입니다.

## 측정 방법

- **패키지 실행 기준:** 에디터가 아닌 Windows Development 패키지를 스크립트로 실행했습니다(`scripts/performance/p4_trace.py`). 15초 워밍업 뒤 8초 동안 좌우 이동(A 2초 / D 2초 × 2)을 자동 입력하고, 무적·사격 없음으로 조건을 고정했습니다.
- **두 가지 계측:** CSV 프로파일러(프레임·스레드 시간)와 Unreal Insights trace(trace 서버 방식, CPU·GPU 스코프)를 같은 8초 구간에서 함께 기록했습니다. 구간은 trace region으로 표시했습니다. GPU는 큐별(그래픽 / 비동기 컴퓨트) 점유 시간까지 집계했습니다.
- **교란 줄이기:** 조건을 기준 → 변경 → 변경 → 기준처럼 교차해 실행하고, 묶음의 첫 회차는 버렸습니다(첫 회차가 1.1배 이상 느려지는 일이 반복됐습니다). 바뀌지 않아야 할 패스(예: 해상도와 무관한 패스)를 대조로 두고, 대조가 ±2%를 넘게 흔들린 회차는 GPU 비교에서 뺐습니다.
- **실제 적용값 검사:** 회차마다 바꾼 설정의 실제 값과 설정 출처를 게임 로그로 다시 읽고, 다르면 워밍업 전에 멈췄습니다. `ProfileGPU`로 실제 업스케일러와 내부 해상도도 확인했습니다. 이 검사로 잡은 사례:
  - 패키지 게임이 종료할 때 품질 설정을 저장해, 다음 "기준" 회차가 High로 시작한 문제(P7-01)
  - 배율 132% 환경에서 게임이 1935×1089로 렌더링되던 문제(P4-02, 게임 프로세스에만 DPI 호환 레이어 적용)
  - 프로젝트 설정이 품질 그룹보다 우선하는 두 값(텍스처 풀, 그림자 바이어스)

## 핵심 결론: 그래픽 큐가 임계 경로

![TSR 장면의 그래픽·비동기 컴퓨트 큐](../media/perf-p5-02/insights-tsr1-graphics-compute.webp)

*Insights GPU 타임라인(P5-02). 위 `GPU0-Graphics0`은 프레임 내내 작업하고, 아래 `GPU0-Compute0`은 Lumen GI·CAS를 처리한 뒤 프레임 끝에서 약 3.9 ms 기다립니다.*

- 그래픽 큐는 프레임 내내 작업하고(대기 약 0.4 ms), 비동기 컴퓨트 큐는 Lumen GI(ScreenProbeGather 등)와 VRS 이미지를 처리한 뒤 약 4 ms를 기다립니다.
- 그래서 **비동기 컴퓨트 쪽 절감은 Frame에 전달되지 않고, 그래픽 큐 쪽 절감만 전달됩니다.** 위 결과가 모두 이것으로 설명됩니다.
  - CAS를 꺼도 Frame 불변(P4-05)
  - 같은 해상도에서 업스케일 패스가 0.57 ms 줄어도 전체는 0.13 ms(P5-01, TSR 일부가 비동기 큐에서 돎)
  - 해상도를 낮춰 패스들이 1.3 ms 넘게 줄어도 Frame은 0.44 ms(P5-02, 줄어든 Lumen이 비동기 큐)
  - RR의 증가분이 그래픽 큐 증가와 같은 크기(P6-01, 8초 구간 전체를 큐별로 집계)
- 품질을 Medium까지 낮춰도 그래픽 큐가 계속 임계 경로였습니다. 비동기 큐의 여유는 그림자까지 끈 Low 수준에서야 2 ms로 줄었습니다(P7-01).

## 보급형 사양 대응

|---|---:|---:|---:|---:|---|
| Epic (3, 기준) | 12.20 | 13.05 | 12.62 / 0.40 | 8.30 / 4.73 | — |
| High (2) | 11.08 (−9%) | 11.96 | 11.52 / 0.43 | 7.14 / 4.80 | 차이 거의 없음 |

| Low-B (0, GI만 1) | 6.37 (−48%) | 7.78 | 7.36 / 0.42 | 5.81 / 1.96 | 매우 나쁨(그림자 꺼짐) |

(프레임당 ms, 조건별 2회 평균. 큐 점유는 표본 구간의 GPU 스코프 합집합, 대기는 프레임 길이 − 점유.)

- **해상도보다 기능 단계가 효과적입니다.** 내부 픽셀을 32% 줄여도(TSR 60.6% → DLSS 50%) GPU는 3.8%만 줄었지만(P5-02), 품질 Medium은 24%를 줄였습니다(P7-01). 그림자·드로우·포스트 프로세스처럼 그래픽 큐에 남는 비용이 해상도와 무관하게 크기 때문입니다.
- **화질 판단(직접 플레이하며 단계 전환):** High까지는 차이를 거의 못 느낌, Medium부터는 차이가 보이지만 허용 가능, 그림자가 꺼지는 Low는 매우 나쁨.
- 보급형 GPU(RTX 4060·3060급)의 실제 FPS는 측정하지 않았습니다. 이 결과는 "이 장비에서 낮출 수 있는 여지"이며 보급형 수치는 추정입니다.

## 채택한 변경과 기각한 시도

- **채택:** 텍스처 풀 2048 MiB·그림자 바이어스 −1.0(P2), 적 메시만 RT 제외(P4-04, `AEnemyCharacter`에서 `bVisibleInRayTracing=false`). DLSS 플러그인은 설치·동작을 확인했지만 기본 업스케일러는 TSR로 두었습니다.
- **기각:** RT LOD 바이어스(이중 스키닝으로 손해), CAS 끄기(비동기 큐라 효과 없음), DLSS RR(+8% 비용으로 반사 선명도를 얻는 화질 옵션이라 기본값으로 쓰지 않음). 캐릭터 이동 CPU 최적화는 GameThread가 병목이 아니어서 진행하지 않았습니다.

## 한계

- 대부분 trace를 켠 수치입니다. 조건별 2회·8초 표본이고, 맵마다 한 장면입니다. 서로 다른 날·묶음의 절댓값은 비교하지 않고 같은 묶음 안의 차이만 씁니다.
- trace를 켠 실행은 종료 코드 777003(CrashReporterCrashed)으로 끝납니다. 원인은 조사하지 않았고 trace 데이터는 정상 분석됐습니다.
- 측정 PC의 Windows 배율(약 132%) 때문에 측정 시 게임 프로세스에만 DPI 호환 레이어(`HighDpiAware`)를 적용했습니다.
- VRAM 사용량은 측정하지 않았습니다.

## 진행 중 조정한 점

- 적 수 증가 분석(P4)은 첫 시도의 파일 기록 trace가 종료 크래시로 끝나, trace 서버 방식으로 수집 방법을 바꾸고 진단부터 다시 했습니다.
- 보급형 사양에서의 대응 여지를 확인하려고 품질 프리셋 비교(P7)를 추가했습니다.
